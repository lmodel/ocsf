# Explanations

* [Numbers stay numbers](numbers-stay-numbers.md) - Why an enumerated attribute is an integer with an `any_of` of `equals_number`, and not a LinkML enum: OCSF writes `activity_id: 1`, and a LinkML enum's values are strings, so no real event could satisfy one.
* [Profiles and what JSON Schema cannot see](profiles.md) - Why a profile's attribute is declared on a class and never required by LinkML: OCSF applies it only to an event that lists the profile in `metadata.profiles`, which JSON Schema cannot see from inside an object, so `tests/ocsf_rules.py` checks it.
* [A data type's regex](data-type-regex.md) - Why the JSON Schema refuses a value past its data type's regex although OCSF's validator only warns: a LinkML pattern cannot warn. So 5 of the 93 events in ocsf/examples pass OCSF's validator and fail here.
* [How the schema is written](how-the-schema-is-written.md) - Why a script writes the schema from two inputs: what OCSF's compiler makes of the tag, which resolves `extends`, `$include`, patches and the datetime siblings as OCSF means them, and the tag's source files, for what the compiler folds away.
* [What OCSF leaves open](what-ocsf-leaves-open.md) - Why `OcsfObject` and `OcsfJsonValue` have the class URI `linkml:Any`, what that admits beyond OCSF, and how a `json_t` slot takes an array, which LinkML's `Any` leaves out.
* [Rules beyond JSON Schema](rules-beyond-json-schema.md) - What `tests/ocsf_rules.py` checks because JSON Schema looks at one object at a time: profiles, `type_uid`, observable names, path constraints, enumerated array labels, data type lengths and `metadata.version`, each under the name OCSF's validator gives it.
* [Mappings](mappings.md) - How the schema crosses to other vocabularies: close mappings from the CVE, CWE and ATT&CK objects, exact mappings on keys that hold the same value in the same form, and related mappings to the D3FEND terms OCSF's references name. No SSSOM file sits beside the schema.
* [Python models](python-models.md) - What the generated Python models do with an event: the Pydantic models load every example, and the dataclasses have two gaps in LinkML 1.12.1, a key named after a Python keyword and a JSON value.
* [RDF](rdf.md) - How to get RDF from an event: apply the generated JSON-LD context, which gives each key its IRI under `https://w3id.org/lmodel/ocsf/`. Nothing in OCSF identifies an event, so it and its objects are blank nodes.
* [What OCSF's files get wrong](ocsf-faults.md) - Five things in OCSF 1.9.0 that needed a decision: the misspelled class `event_log_actvity`, its constraint on an attribute it lacks, `patch_state`'s constraint on paths, which OCSF's validator fails on every such event, one reference address with a stray `href='`, and a `datetime_t` example its own regex refuses.
* [What the schema does not cover](scope.md) - What the schema leaves out: OCSF's other extension repositories, a source event's own class and the event bundle encoding. It says nothing about whether what an event claims is true.
